# Sport: a multi-agent AI operations system for a one-person company

**A Chief-of-Staff layer that coordinates venture leads and specialist workers across every project, with a human approval gate on anything that leaves the machine.**

Most people try to make one model smarter. I went the other way and split the work across named agents that each keep their own memory, their own skills and their own conversation history, then made them coordinate through a shared task bus. Sport is the orchestration layer on top: an executive coordinator that decomposes a goal into cards, assigns each card to the specialist that should own it, and expresses the dependencies between them as edges rather than as polite requests in a prompt. It is the part of this portfolio that keeps the rest of it moving when nobody is watching.

## What it is
Sport is the operating layer over a fleet of named agents rather than one big prompt. Each agent keeps its own memory, skills and conversation history, and they coordinate through a shared task bus — a SQLite kanban board on this machine. Anything that leaves the machine (posting, email, publishing) stops at an approval gate first. It is the thing that lets the other projects keep running when nobody is watching.

## How it works

- **A fleet, not a monolith** — Seven persistent agents: an executive coordinator (Sport), venture CEOs (goldie for Track My Gold, tradedeck, budgetbycheck) and specialists (dev for engineering, fin for finance, mark for marketing). Each has its own profile, skills and memory.

- **One task bus** — Work is claimed from a kanban board backed by SQLite. A dispatcher spawns the right worker for a card, records heartbeats while it runs, and re-queues a worker that dies without finishing.

- **Orchestrator decomposes** — The coordinator turns a goal into child cards with explicit dependencies, so nothing starts before its inputs exist. It routes; it does not implement.

- **Approval gates on side effects** — Outbound actions land in a review column and wait for a human. An audit trail records every transition, and there is a kill switch.

- **Scheduled work, visible failures** — Cron jobs run the recurring monitoring, research, drafting and reporting. Each one delivers into a surface a human actually reads, so a failure surfaces instead of silently no-op'ing.

- **One front door** — A local router fronts every service (the dashboard, the portfolio, the camera panel, the glasses apps) and is published only over a private tailnet.

## What it costs
The fleet's default path costs nothing per token: local weights and the free-model catalogue carry the volume, and the coordinator's own traffic is light enough to live inside the free Ollama Cloud tier. Paid frontier models exist as an escalation path that has to be chosen on purpose.

## How to build it this way

- **Give each agent its own context** — One profile per role — memory, skills and config — instead of one prompt trying to be everything. Specialist context is what makes a specialist agent good.

- **Put a durable task bus in the middle** — SQLite is enough. Workers claim and complete through tools, never by shelling out to the board CLI.

- **Model dependencies as edges** — A card waits on its parents. That one rule removes most coordination bugs.

- **Gate the side effects** — Anything outbound stops at review, with an audit line. Unattended is only safe when the blast radius is bounded.

- **Make every scheduled job report somewhere read** — A cron job whose output nobody sees is a job that fails silently for a month.

## What I learned

- A hierarchy of narrow agents beats one generalist prompt — and it fails locally instead of globally.

- Approval gates are the enabling feature, not the brake: they are what make unattended work acceptable.

- Heartbeats and stale-run recovery are the difference between 'runs unattended' and 'sometimes just stops'.

## FAQ

### Why use several agents instead of one assistant with more tools?
Because of blast radius. A generalist with every tool loaded can break anything it touches and its failures are hard to trace. Narrow agents own small surfaces, keep their own context, and can be replaced or retried individually. The hierarchy also means an agent that is good at research never has to hold the credentials for publishing.

### How do the agents hand work to each other?
Through a shared task bus, in this case a SQLite board on the same machine. A card carries the goal, the assignee and its dependencies. Dependencies are modelled as edges, so a card promotes to ready only when its parents are actually done. That is what lets an orchestrator fan work out and fan results back in.

### What stops an agent from posting or emailing something wrong?
An approval gate. Anything with an external side effect, publishing, outbound messages, account changes, stops and waits for a human decision that arrives in a surface I actually read. The gate is not a brake on the automation, it is the reason the automation is acceptable to run unattended.

## Where to see it
Internal — the coordinator and its dashboard expose personal finances, the vault and live agent state, so this one is not published.

# Home Assistant on a Raspberry Pi, driven by plain English

**A private edge hub where you type what you want the house to do, and a scheduled agent writes, validates and deploys the genuine Home Assistant automation.**

This is a Raspberry Pi 5 running Home Assistant in Docker, with Mosquitto and ESPHome alongside it, reachable only over a private tailnet and never from the public internet. The hub itself is ordinary. What is not ordinary is the layer on top of it: a plain-English automation builder. You type or dictate what you want the house to do, the request becomes a job, and a scheduled agent writes the real Home Assistant automation, validates it against the config API, reloads Home Assistant, and writes the outcome back to a dashboard so you can see whether it actually took. It is event-driven, so it does nothing and costs nothing until you ask it for something.

## What it is
A Raspberry Pi 5 ('tmgedge') running Home Assistant in Docker, with Mosquitto and ESPHome alongside it, reachable over a private tailnet and never the public internet. On top of it is the interesting part: a plain-English automation builder. Type or dictate what you want the house to do and a scheduled agent writes the real Home Assistant automation, validates it against the config API, reloads, and writes the outcome back to the dashboard. Event-driven and silent when idle.

## How it works

- **Ask in plain English** — A text box on the custom dashboard, or dictation — 'when the front door camera sees a person after 10pm, flash the porch light and tell me'.

- **Queued as a job** — The request becomes a card on the task bus, so the work is traceable and retryable instead of a one-shot prompt in a chat window.

- **An agent writes real YAML** — A scheduled agent picks it up and writes the automation against the actual entity ids on the hub, not invented ones.

- **Validated before it is live** — The automation is checked through Home Assistant's config API first. Only a passing config is reloaded — a bad automation never reaches the running house.

- **Result reported back** — Success or the validation error is written to the dashboard, so the failure mode is a message, not a light that never flashes.

- **Backups that have been tested** — A nightly job mirrors the Home Assistant configuration to a second machine, and the restore drill has actually been run.

## What it costs
This is the cheapest project in the portfolio to run: the hub is a one-off Raspberry Pi, the model is touched only when you ask for an automation, and the house itself is controlled locally. One genuine third-party cost exists if Nest cameras come in — Google's Device Access programme is a $5 one-time fee.

## How to build it this way

- **Keep the house off the internet** — Home Assistant on the tailnet only. Never port-forward it; the convenience is not worth the attack surface.

- **Validate before you reload** — Use the config API as a gate. One malformed automation can take down every other automation you own.

- **Make the agent idempotent** — Re-running a request should either do nothing or fix the automation — not append a second copy.

- **Mirror the config nightly** — And restore it once, on purpose, before you need to.

- **Watch the things you would notice** — The watchdog automations that earn their keep: media player left on, backup going stale, doors after dark.

## What I learned

- The house is a hard boundary: private by default, validated before it goes live.

- Event-driven beats always-on — silence is both the security posture and the cost model.

- A backup you have never restored is a hope, not a backup.

## FAQ

### Why a Raspberry Pi instead of a cloud service?
Because the hub is a one-off box and the control path is local. Home Assistant, Mosquitto and ESPHome all run on the Pi, so the house keeps working when the internet does not, and nothing about the house is exposed to the public internet at all.

### What happens if the agent writes a broken automation?
It is never loaded. The generated YAML is validated against the Home Assistant config API before the reload step, so a bad automation fails at validation and is reported back on the dashboard rather than taking the hub down.

### What is actually running on it today?
A morning weather and sunrise briefing, a shopping-list reminder, a left-on watchdog for the media player, and an automatic-backup staleness alert. Alongside those, the config is mirrored to a second machine every night with a restore path that has been tested rather than assumed.

## Where to see it
Tailnet only, by design — the hub is deliberately not reachable from the public internet.

The full write-up, the build steps and the screenshots are on the [project page](https://sport.taila73942.ts.net/portfolio/project/smart-home-hub.html).

# Track My Gold: a YouTube engagement and affiliate dashboard

**A content-operation dashboard that surfaces video performance, queues comments and engagement for review, tracks affiliate revenue and drives the content calendar.**

Track My Gold is the operating dashboard behind a gold-prospecting content channel. It surfaces video performance, runs an approval queue for comments and engagement, tracks affiliate revenue, checks search performance and feeds the weekly content calendar. The single most important design decision is where the post actually happens: comments go out through the YouTube API from the approve button itself, not from a scheduled session that may already have finished. Search Console feeds a live SEO tab under a read-only OAuth scope, so the view of search is never more stale than the last refresh. The public product side is trackmygold.net.

## What it is
A content-operation dashboard for a gold-prospecting channel: it surfaces video performance, runs an approval queue for comments and engagement, tracks affiliate revenue, checks SEO and drives the content calendar. Comments are posted through the YouTube API from the approve button itself — not from a cron session that may already have finished. Search Console feeds a live SEO tab under a read-only OAuth scope. The product side is trackmygold.net.

## How it works

- **Discovery** — A scheduled job finds newly published videos in the target niche and pushes candidates into the dashboard, each with a draft comment drawn from an approved library.

- **Review queue** — Nothing goes out unreviewed. Comments are edited, approved or discarded on the dashboard — the human step is the product decision, and it is enforced by design.

- **Approve = post** — The approve button calls the YouTube API directly and then writes the result into the tracking store, so the UI cannot drift from reality.

- **Measure** — A weekly job pulls trials, churn and channel metrics; an SEO tab reads Search Console impressions and queries; affiliate review runs weekly.

- **Publish** — Approved content hands off to the publishing pipeline (Buffer / the blog) instead of being copied around by hand.

## What it costs
The recurring work runs on the free tier, and the platform APIs used (YouTube data, Search Console read-only) add nothing to the bill. The real cost of this project is attention — which is why the approval queue exists.

## How to build it this way

- **Put the API call inside the button** — Do not route an action through a session that might have exited. Clicking approve should be the same thing as posting.

- **Reconcile against the raw record** — The UI should re-derive posted state from the tracking file on load, so a crash mid-write cannot leave it lying.

- **Deliver jobs somewhere a human reads** — Not a fire-and-forget webhook.

- **Make the niche search a job, not a habit** — Discovery belongs on a schedule with a review gate.

- **Measure the funnel, not the toil** — Impressions, trials, conversions by channel. The vanity number hides the leak.

## What I learned

- The bottleneck was acquisition, not integration — the dashboard proved that quickly and honestly.

- A dashboard that silently drifts from the underlying data is worse than no dashboard.

- Approvals in a web surface the person actually uses beat a webhook nobody reads.

## FAQ

### Why post comments from a button instead of a scheduled job?
Because the scheduled session may already have ended by the time the decision is made. Putting the API call inside the approve button means the action happens in the same context as the approval, so it either really posted or it visibly failed at the moment I clicked.

### How is the SEO data kept current?
Search Console feeds a live tab under a read-only OAuth scope, and the panels are refreshed on a schedule. Read-only matters: the reporting side never needs write access to the search property to be useful.

### What does the approval queue actually hold?
Outbound engagement that needs a human decision, comment replies and similar actions, presented so they can be reviewed, edited and approved in one pass. It is the reason the channel can be worked in batches instead of being babysat.

## What it is
An AI content pipeline that drafts, reviews, approves and publishes on a schedule — built so the machine does the volume and the human keeps the judgement. Drafts arrive with review/edit/redo controls, approved items hand off to scheduling, and the review surfaces include wearable targets (Meta Ray-Ban Display, Quest). The same engine runs the blog job that drafts one post every three days.

## How it works

- **Topic queue** — A roadmap file holds the queue. The job takes the next item and flips it to drafted, recording the resulting post id — so the same topic cannot be picked twice.

- **Draft** — An agent writes the full post as HTML in a house style, from a fixed set of real links and facts.

- **Offline gates** — Before a human ever sees it: a format gate (structure, image sizing, link attributes) and a duplicate guard that fails the draft if it reuses too much prose from an earlier post.

- **Review, edit, redo** — The reviewer edits in the app or the editor; edits are mirrored back into the source file so the next regeneration cannot silently revert them.

- **Publish** — Only approved content ships — to the scheduling API or as a blog draft. Publishing is a separate, explicit step.

## What it costs
Cost is dominated by drafting tokens, which is why the guard rails are deterministic: the checks that protect quality run for free, offline, before any model time is spent.

## How to build it this way

- **One source-of-truth file per post** — Keep the authored HTML in a durable workspace and treat the editor as a renderer.

- **Gate before review** — Format and duplicate checks are cheap and deterministic — run them so a human never reviews something structurally broken.

- **Mirror every editor-side edit back** — Changes made in a UI exist only in that UI until you write them back.

- **Strip the house footer before similarity scoring** — Otherwise every post looks like a duplicate of every other post.

- **Leave it a draft** — Draft is the correct resting state for machine-written prose.

## What I learned

- Guard rails are cheaper than re-editing: measure similarity and structure offline, not with a model.

- 'Human in the loop' only counts if the human's edits survive the next run.

- Design for the review surface you will actually use — glasses and tablets included.

Format and duplicate detection, run as plain scripts with zero tokens involved. Similarity scoring is done offline and the house footer is stripped before scoring so the site's own boilerplate does not make every post look alike.

Because the review surface you actually use decides whether approval happens. Designing the controls so they work in a constrained viewport with arrows rather than a pointer means the queue gets cleared wherever I happen to be, not only when I am at a desk.

It hands off to social scheduling and stays a draft until it is explicitly published, so approval and publication remain two separate decisions rather than one button that does both.

# Token Killers: cutting AI API spend without cutting quality

**An audit-and-rebuild service for teams bleeding money on AI APIs, where the numbers come from a stack that is already running rather than from a spreadsheet.**

Token Killers is the cost-engineering side of this portfolio: an audit and rebuild service for teams whose AI bill has outgrown the value they get from it. The method is unglamorous. Baseline what is actually being spent, find the fat, compress the prompts and the context, route each task to a model that is big enough rather than to a model that is impressive, and offload the boring majority of the traffic to local weights. ## What it is
An audit-and-rebuild service for teams bleeding money on AI APIs: prompt and context compression, model routing, caching, and local-model offload — with a before/after calculator that proves the delta. The credibility comes from the fact that the same stack runs on this machine, so the numbers are measured rather than theorised.

## How it works

- **Baseline** — Measure real tokens in and out per workload. Most teams are guessing; the bill is the only honest benchmark.

- **Find the fat** — Repeated context in every call, system prompts longer than the task, and frontier models selected for work a small model would do.

- **Compress and route** — Cut the context to what the task needs, cache the stable part, and route each call to the cheapest model that can pass its checks.

- **Offload the volume** — Deterministic, high-volume work (classification, extraction, formatting) moves to local weights: same result, no per-token fee, no data leaving the machine.

- **Prove it** — Re-measure on the same workload and publish the before/after. If the saving is not measurable, it did not happen.

## What it costs
Worked example at 1M input + 0.25M output tokens a month: on gpt-5.5 that is $12.50; the same volume on deepseek-v4-pro is about $0.45; routed to the free catalogue or a local model it is $0. Prices are the providers' published per-million-token rates read on 2026-10-16.

## How to build it this way

- **Instrument first** — Log tokens and model per call before changing anything. You cannot optimise a bill you have not attributed.

- **Treat context as a budget** — The cheapest token is the one you never send. Stable prefixes should be cached, not re-sent.

- **Route by task, not by habit** — Keep a cheap tier for extraction and routing and a frontier tier for judgement, and make the escalation explicit.

- **Offload the boring 80%** — High-volume classification and formatting belong on local weights — that also keeps the data home.

- **Re-measure, then publish** — A saving you cannot show on a graph is a claim, not a result.

## What I learned

- Most of an AI bill is context you did not need and a model that was too big for the job.

- Local offload is a privacy feature as much as a cost feature.

- Routing is the highest-leverage single change — the spread between tiers is an order of magnitude.

# Hermes Vision: a live AI agent session on phone and glasses

**A progressive web app that puts a running agent session on a phone or on display glasses, and treats model choice as a client-side switch.**

Hermes Vision is a progressive web app that takes a live agent session and puts it on a phone or on display glasses: pick up or start a session, choose a model, stream the reply. The engineering that matters is the realtime layer, server-sent events with named event types, and the input model. On glasses there is no pointer and the viewport is fixed, so every control has to be reachable with arrows alone. That constraint produced a 2-D grid you navigate with a D-pad, focus paging, and a T9-style keyboard, none of which I would have designed if I had started from the phone.

## What it is
A progressive web app that puts a live agent session on a phone or on Meta Ray-Ban Display glasses: pick up a session, choose a model, stream the reply. The engineering that matters is the realtime layer — server-sent events with named event types — plus a wearable-first input model: a 2-D grid you navigate with arrows alone, focus paging, and a T9-style keyboard.

## How it works

- **Start or resume a session** — The client starts a session against the API and sends the model kind explicitly — hosted provider for speed, local runtime for privacy. An unqualified request must never silently fall back to a local runtime that may not be running.

- **Stream with named events** — The server emits discrete typed events — token deltas, tool start, commentary, message updates, final, close. One transport carries chat, tool calls and status, so the UI can render each differently.

- **Guard the session** — Per-session file locks stop two clients from writing the same conversation at once.

- **Survive a refresh** — A service worker caches the app shell, so the app installs to the home screen and comes back without a reload.

- **Reach every control from a D-pad** — Tab bar and grid navigation are keyboard-only. Up/Down moves within a column of the T9 grid; nothing depends on touch or hover.

## What it costs
Model choice is a switch in the client, which makes cost control a UX feature: the fast hosted tier is the default and the local runtime is one selection away for private or offline use.

## How to build it this way

- **Build the transport once** — Named SSE events give you chat, tool activity and status on a single stream — a single stream is much less code than three.

- **Never default to local by accident** — If the client does not state which runtime it wants, a request can hang against a local server that is not running.

- **Design for arrows only** — Fixed viewport, no scrolling, every control reachable with up/down/left/right and enter.

- **Version the app and its cache together** — A service worker holding a stale shell is the most common 'my fix did not ship' bug.

- **Keep deployments frontend-only** — Shipped update zips only touch the client; the backend carries local work that a generic zip would overwrite.

## What I learned

- Wearable constraints are real engineering: a fixed viewport and no pointer change the whole UI.

- One event stream for chat, tools and status removed an entire class of bugs.

- A stale service worker can make a working deploy look broken — version the cache or chase ghosts.

### Why server-sent events rather than WebSockets?
The traffic is server-to-client streaming of a reply, which is exactly what SSE is for, and named event types let one stream carry chat, tool calls and status updates in the same channel. That single event stream replaced a set of separate channels and removed a whole category of bugs.

### How does model choice work in the client?
It is a switch in the app, which turns cost control into a user-facing feature. The fast hosted tier is the default and the local runtime is one selection away when privacy or offline use matters more than speed.

### What broke first on the wearable?
The input model, predictably. A fixed viewport with no pointer makes a layout that feels fine on a phone unusable. Designing for arrows only, with focus paging, is what made the glasses path actually navigable rather than technically present.

# Autolisting: a visible ten-step pipeline that turns property video into a finished listing

**Upload a property video and a few fields, get back a finished, formatted listing — with every one of the ten pipeline steps visible while it runs.**

Autolisting takes a property walkthrough video and a handful of fields and returns a finished, formatted listing. The pipeline is deliberately visible: ten named steps with live state, so the user can see exactly where the machine is and step in when needed. Under the hood it is a chunked uploader that survives an interrupted tunnel, a local ffmpeg and Python worker that probes the media before touching it, a framing and enhancement pass that straightens shots and maps their tone, and an LLM writing the copy from what the frames actually show.

## What it is
Upload property video and a few fields, get back a finished, formatted listing. The pipeline is deliberately visible — ten named steps with live state — so the user can see exactly where the machine is and step in when needed. Under the hood it is a chunked uploader, an ffmpeg/Python worker, a framing and enhancement pass, and an LLM writing the copy.

## How it works

- **Chunked upload** — The front end splits the file into 4 MB chunks and PUTs each one at its byte offset with retries. A single large PUT is all-or-nothing and dies on a long tunnel; chunking makes uploads resumable and survivable.

- **Probe before processing** — The server verifies the file it owns before starting work — a video whose index never arrived fails immediately with a real message instead of hanging.

- **Extract frames** — A Python worker pulls frames with ffmpeg, using absolute tool paths because a launchd environment does not have Homebrew on PATH.

- **Straighten and enhance** — Each frame is squared up (roll plus vertical perspective) and run through an enhancement pass, so phone footage reads like a listing rather than a walkthrough.

- **Write the copy** — An LLM turns the structured facts into the listing text; the images stay deterministic image processing, not generation.

- **Always write a verdict** — Every job ends in a terminal state — ready or failed — and a sweeper picks up jobs that were uploaded but never started. 'Processing forever' is treated as a bug class, not a state.

## What it costs
The expensive half of this pipeline is compute, not tokens — frame extraction and enhancement — and it runs on this machine, so a finished listing costs local machine time plus a single short generation. Nothing is billed per uploaded megabyte.

## How to build it this way

- **Chunk your uploads** — Anything over a few megabytes over a tunnel needs resumable chunks with explicit offsets.

- **Probe media before you trust it** — A video without its index is indistinguishable from a hang until you check.

- **Always write a terminal state** — Ready or failed, every job needs a verdict or the UI polls forever.

- **Sweep for orphaned jobs** — A periodic sweeper that resumes 'uploaded but never started' work is what turns an occasional failure into a non-event.

- **Resolve tool paths explicitly** — Servers started by launchd get a minimal PATH; a bare ffmpeg call fails there and works perfectly by hand.

## What I learned

- A job that never writes its verdict looks like a hang, not an error — design the failure state first.

- An interrupted upload leaves a clean prefix, so you cannot tell it from a bad source file: instrument the upload itself.

- Straightening and tone-mapping are what make a phone walkthrough look like a listing.

### Why is every step shown to the user?
Because a job that never writes a terminal state looks like a hang, not an error. Ten named steps with live state, and an explicit ready-or-failed verdict, mean the UI never polls forever and the user can see where to intervene.

### How does the video get in and out?
Anything over a few megabytes over a tunnel goes up as resumable chunks with explicit offsets; the worker probes the file before processing, extracts frames, straightens and enhances them, and one low-cost catalogue model writes the listing copy in a single generation.

# Obsidian Brain: a live 3D graph of a note vault, built without a single model call

**A live 3D visualization of a personal knowledge vault, derived deterministically from the notes themselves and regenerated on demand.**

Obsidian Brain renders a personal knowledge vault as a live 3D graph you can search and drill into. A Python pass walks the notes and their links and writes one graph payload; a WebGL viewer turns that into an explorable structure. The deliberate choice is that no model is involved anywhere in the build or the viewer: the graph is derived deterministically from the source notes, so it is always current and never invented. Connection count, folders and links are already sitting in the vault as free metadata, and they turn out to be a surprisingly good relevance signal.

## What it is
A live 3D visualization of a personal knowledge vault. A Python pass walks the notes and their links and writes a graph payload; a WebGL viewer renders it as an explorable structure with search and drill-down. The deliberate choice here is that no model is involved at all — the graph is derived deterministically from the source notes, so it is always current and never invented.

## How it works

- **Walk the vault** — A generator reads the note tree and parses links between notes.

- **Build the graph** — Nodes and edges are written to a single JSON payload, sized by how connected each note is and clustered by the structure the vault already has.

- **Render it** — A static WebGL viewer loads the payload — no server-side rendering, no database.

- **Navigate** — Search highlights a note; drill-down walks its connections, which is how you find the note you forgot you wrote.

- **Regenerate on demand** — Because it is a generator, running it again is the whole 'sync' story.

## What it costs
This is the one project in the portfolio with a genuinely $0 AI bill: no model runs anywhere in the build or the viewer. That is the point — some problems are structure problems, and calling an LLM at them just adds noise.

## How to build it this way

- **Generate, never hand-maintain** — A graph a human has to update is a graph that is wrong within a week.

- **Ship one payload** — A single JSON file keeps the viewer static and portable.

- **Cluster with structure you already have** — Folders and links are free metadata — use them before inventing embeddings.

- **Make search the primary control** — Exploration is the demo; finding the thing you actually wanted is the product.

## What I learned

- Not every problem is a prompt — the best answer is sometimes a deterministic build.

- A visualization of your own notes is only useful if it regenerates itself.

- Connection count is a surprisingly good relevance signal for free.

### Why visualize notes instead of just searching them?
Because connection count is a free relevance signal, and a graph makes structure you already have — folders and links — visible. It is only useful if it regenerates itself, which is why nothing in it is hand-maintained.

### How does the graph stay current?
A walker rewrites a single JSON payload from the notes and links on demand, and the viewer is static over that file. Clusters come from folders and links rather than invented embeddings, so the graph never drifts from the vault it describes.

# CNBC live on the Meta Ray-Ban Display: a proxy in front of a Referer-gated CDN

**A live CNBC stream on 600x600 glasses with D-pad navigation only — and a local proxy that exists because the upstream CDN only serves its playlist to the right Referer.**

This project puts a live CNBC feed on the Meta Ray-Ban Display glasses: a 600x600 viewport, D-pad only, streaming from a free feed that needs no login. The player is not the interesting part. The upstream CDN only serves its playlist when the request carries the right Referer header, which a glasses webview cannot fake, so a small local proxy sits in front of it: it re-arbitrates the best CDN host and caches that choice with a long TTL, rewrites the playlist so every segment URL is same-origin, and streams the bytes through without ever buffering a whole segment in memory.

## What it is
Live CNBC on the Meta Ray-Ban Display glasses: 600x600, D-pad only, a free no-login feed. The interesting engineering is not the player, it is the proxy in front of it — the upstream CDN only serves its playlist when the request carries the right Referer, which a glasses webview cannot fake, so a small local proxy re-arbitrates the best CDN host, rewrites the playlist to same-origin URLs and streams the bytes through.

## How it works

- **A local proxy stands in front** — A dependency-free Python service binds to localhost and fronts the stream, so the glasses only ever see one origin.

- **Re-arbitrate and cache the host** — The proxy asks the provider's own server list for the best CDN host, then caches that choice — a cold first request pays a full round trip, a warm one does not.

OpenClaw: a local agent gateway, configured in one auditable file

A multi-channel AI gateway that runs as a local process, mounts behind the Command Center router, and declares its agents, tools, plugins, channels and bindings in one file.

OpenClaw is a multi-channel AI gateway with extensible messaging integrations. It runs locally as a gateway process and is served through the Command Center router, which rewrites the control UI's base path and starts the gateway on demand if it is not already running. Its configuration declares agents, tools, plugins, channels and bindings in one file, which is what makes it the plumbing layer that connects agents to messaging surfaces: reachability is a configuration fact rather than something scattered across code.

What it is

OpenClaw is a multi-channel AI gateway with extensible messaging integrations, running locally as a gateway process and served through the Command Center router, which rewrites the control UI's base path and starts the gateway on demand if it is not already running. How it works

  • Gateway process — A local gateway serves the control UI and its API on its own port.
  • Configuration as one file — Agents, models, tools, plugins, channels and bindings are declared in a single JSON config, kept with numbered backups.
  • Channels and bindings — Messaging integrations are bound to agents, which is what turns an agent into something reachable from a chat surface.
  • Mount behind a prefix — The router sets the app's base path, rewrites its asset and favicon URLs, and auto-launches the gateway when the route is first requested.

What it costs

The gateway is free to run locally; spend only appears through the model providers its agents are configured to use, which keeps the routing decision (and the bill) in one explicit config file.

How to build it this way

  • Mount a local UI under a prefix properly — Set the app's own base path and rewrite asset URLs — otherwise you get a page that loads and a stylesheet that 404s.
  • Start on demand — Auto-launching a gateway when its route is first requested avoids keeping a daemon alive for nothing.
  • Keep numbered config backups — One JSON file is easy to read and easy to break; keep the last-known-good copy.
  • Treat the gateway as plumbing — The value is in the bindings and tools, not the process.

What I learned

  • One config file means one place to audit what an agent can reach.

# Muse Prototypes: the same 3D world, packaged to be opened rather than deployed

**A shareable link to the TrackMyGold Frontier world: find the character, accept quests, explore the realm — the same content as the live 3D world, in the form easiest to send.**

Muse Prototypes packages the TrackMyGold Frontier world — western town, gold mine, saloon and forge — as a shareable prototype you can open from a link. Find the character, accept quests, explore the realm. It is the same world definition as the live 3D build, shipped in the form that is easiest to send to someone for feedback, with the same agents inside and the same dialogue path as the tailnet version.

## What it is
The TrackMyGold Frontier world — western town, gold mine, saloon and forge — packaged as a shareable prototype you can open from a link. Find the character, accept quests, explore the realm. It is the same content as the live 3D world, shipped in the form that is easiest to send to someone for feedback.

## How it works

- **One world definition** — Scene, characters and quests come from the same build that serves the live 3D world, so the prototype cannot drift from it.

- **Packaged for sharing** — Exported as a prototype build behind a public share link — no install, no account.

- **Same agents inside** — Characters still talk over the agent stream; the prototype is a surface, not a mock-up.

- **Also live on the tailnet** — The same world is served at its own route for full-fidelity use.

## What it costs
$0 to host and $0 to render — the only metered part is dialogue, exactly as in the live world.

## How to build it this way

- **Ship one definition to many surfaces** — Game, VR entry point, prototype link: all the same content, different packaging.

- **Prefer a share link for feedback** — A link gets opened; a deploy gets deferred.

## What I learned

- Prototypes exist to shorten the feedback loop — optimise for opening, not for fidelity.

- One world definition shipped to several surfaces is far cheaper than rebuilding for each.

## FAQ

### What is in the prototype?
The TrackMyGold Frontier world: a western town, a gold mine, a saloon and a forge, with the same characters and agents as the live build. Find the character, accept quests, explore.

### What does it cost to host?
$0 to host and $0 to render — static assets in the browser. The only metered part is character dialogue, which runs through the same selectable agent provider as the live world.

### Why ship a prototype instead of the live build?
Because a link gets opened and a deploy gets deferred. Shipping one world definition to a share link, the game and the VR entry point is the cheap way to get feedback, rather than rebuilding content per surface.
