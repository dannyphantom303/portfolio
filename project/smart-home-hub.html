THE PROJECT

What it is and why it exists

A Raspberry Pi 5 ('tmgedge') running Home Assistant in Docker, with Mosquitto and ESPHome alongside it, reachable over a private tailnet and never the public internet. On top of it is the interesting part: a plain-English automation builder. Type or dictate what you want the house to do and a scheduled agent writes the real Home Assistant automation, validates it against the config API, reloads, and writes the outcome back to the dashboard. Event-driven and silent when idle.

Highlights

  • Plain-English to working automation: type or speak a request and a scheduled agent writes, validates and deploys it, then reports the result back
  • Custom dashboard rather than the stock overview — the builder, the live automation list, hub health and backup status on one page, served over a private tailnet and never the public internet
  • Nightly configuration mirror to a second machine with a tested restore path
  • Running today: morning weather and sunrise briefing, shopping-list reminder, a left-on watchdog for the media player, and an automatic-backup staleness alert
HOW IT WORKS

The mechanism end to end

No hand-waving: this is the actual chain, in the order it runs.

01

Ask in plain English

A text box on the custom dashboard, or dictation — 'when the front door camera sees a person after 10pm, flash the porch light and tell me'.

02

Queued as a job

The request becomes a card on the task bus, so the work is traceable and retryable instead of a one-shot prompt in a chat window.

03

An agent writes real YAML

A scheduled agent picks it up and writes the automation against the actual entity ids on the hub, not invented ones.

04

Validated before it is live

The automation is checked through Home Assistant's config API first. Only a passing config is reloaded — a bad automation never reaches the running house.

05

Result reported back

Success or the validation error is written to the dashboard, so the failure mode is a message, not a light that never flashes.

06

Backups that have been tested

A nightly job mirrors the Home Assistant configuration to a second machine, and the restore drill has actually been run.

BUILD IT YOURSELF

The steps in order, with the traps

This is the short version of what I would do again — including the parts that bit me first.

01

Keep the house off the internet

Home Assistant on the tailnet only. Never port-forward it; the convenience is not worth the attack surface.

02

Validate before you reload

Use the config API as a gate. One malformed automation can take down every other automation you own.

03

Make the agent idempotent

Re-running a request should either do nothing or fix the automation — not append a second copy.

04

Mirror the config nightly

And restore it once, on purpose, before you need to.

05

Watch the things you would notice

The watchdog automations that earn their keep: media player left on, backup going stale, doors after dark.
